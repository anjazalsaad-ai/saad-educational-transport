# قاعدة بيانات النسخة التجريبية — منصة السعد للنقل التعليمي

## النطاق
- قاعدة البيانات المعتمدة للتصميم: Firebase Authentication + Cloud Firestore.
- لا يتم إرسال SMS في هذه المرحلة.
- لا تُدخل أسماء أو أرقام جوالات أو بيانات أطفال حقيقية.
- لا توجد مدفوعات أو حجوزات ملزمة في النسخة التجريبية.
- نشر قواعد الأمان وحده لا ينشئ مشروع Firebase ولا يربط الموقع بقاعدة فعلية.

## المجموعات المقترحة
### users/{uid}
- uid: معرّف Firebase Auth.
- role: guardian أو captain؛ لا يقبل admin من واجهة المستخدم.
- displayName: اسم تجريبي.
- phone: رقم تجريبي فقط قبل تفعيل المصادقة الهاتفية.
- city: مدينة المستخدم.
- status: demo_pending أو active أو suspended.
- availability: متاح أو غير متاح، للكابتن فقط.
- demo: true.
- createdAt / updatedAt: توقيت خادمي.

### serviceRequests/{requestId}
- guardianUid, captainUid (قد يكون null قبل الإسناد).
- city, destinationType, serviceType, priceMonthly.
- status: new, accepted, declined, in_service, completed, cancelled.
- demo: true.
- createdAt / updatedAt: توقيت خادمي.

### activityEvents/{eventId}
- actorUid, actorRole, eventType, targetType, targetId, summary.
- demo: true.
- createdAt: توقيت خادمي.
- سجل إضافي للأحداث المهمة. القواعد تمنع تعديل الحدث أو حذفه من العميل؛ سجل إنتاج موثوق يتطلب كتابة أحداث من جهة خادمية.

## صلاحيات الإدارة
- لوحة الإدارة يجب ألا تعتمد على إخفاء عناصر الواجهة فقط.
- يتطلب دور الإدارة Firebase custom claim باسم admin=true تُعيّنه جهة موثوقة، مثل Firebase Admin SDK من بيئة آمنة.
- لا تضع مفاتيح Admin SDK أو service account أو أسرارًا في المستودع أو المتصفح.
- لا تمنح مستخدمًا دور الإدارة بتعديل مستند users من الواجهة.
- قواعد Firestore الموجودة في firestore.rules هي نقطة بداية محافظة وليست إثباتًا لاكتمال تدقيق الأمان. اختبرها في Firebase Emulator قبل أي نشر.

## خطوات الربط التي تتطلب حساب مالك المشروع
1. إنشاء مشروع Firebase ضمن الخطة المناسبة، ومراجعة الأسعار وحدود الاستخدام الحالية.
2. إنشاء تطبيق Web ونسخ إعدادات Firebase العامة إلى إعدادات التطبيق (ليست مفاتيح Admin SDK).
3. تفعيل مزود دخول مناسب للمرحلة التجريبية. يمكن استخدام حسابات اختبار أو مصادقة مجهولة؛ لا تستخدم رقم الجوال ككلمة مرور أو كدليل على ملكيته.
4. إنشاء قاعدة Cloud Firestore في وضع الإنتاج، ثم نشر firestore.rules بعد اختبارها.
5. إعداد حساب إدارة بطريقة موثوقة، خارج الواجهة العامة.
6. اختبار فصل حسابات ولي الأمر والكابتن، ورفض قراءة البيانات غير المصرح بها، وعزل لوحة الإدارة.
7. ربط الواجهة بقاعدة الاختبار، ثم نشر تحديث الموقع بعد موافقة المالك والتحقق من سجل البناء.

## حد النسخة الحالية
إنشاء ملفات التكامل والقواعد لا يعني أن قاعدة بيانات سحابية قد أُنشئت أو رُبطت. قبل الربط ستظل أي بيانات محلية في المتصفح ولا تتزامن بين الأجهزة. لا تُعرض الواجهة للمستخدم على أنها قاعدة مشتركة حتى يتم اختبار الكتابة والقراءة من حسابين منفصلين.


## اختبارات قواعد Firestore
أُضيفت اختبارات انحدار أولية في `tests/firestore.rules.test.mjs` لتغطية:
- إنشاء ملف تجريبي خاص بالمستخدم، ورفض دور admin من العميل.
- منع قراءة ملف مستخدم آخر.
- السماح لولي الأمر بإنشاء طلبه التجريبي فقط.
- منع الكابتن من إنشاء طلب بصفته ولي أمر.
- منع تعديل/حذف سجل النشاط من العميل.

لتشغيلها محليًا بعد تثبيت Firebase CLI والاعتماديات:
```sh
npm install
npx firebase emulators:exec --only firestore --project saad-educational-transport-rules-test "npm run test:rules"
```
هذه الاختبارات تحتاج Firestore Emulator؛ لم يتم تشغيلها في بيئة هذا التعديل، لذلك لا تعتبر ناجحة حتى تظهر نتيجة تنفيذ فعلية. لا تنشر القواعد إلى Firebase Console قبل تشغيل الاختبارات ومراجعة أي إخفاق.
