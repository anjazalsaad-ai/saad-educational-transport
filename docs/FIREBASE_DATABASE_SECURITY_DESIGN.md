# منصة السعد للنقل التعليمي — تصميم قاعدة البيانات وقواعد الأمان (مسودة للمراجعة)

- الحالة: **مسودة تصميم فقط — غير معتمدة للتنفيذ**
- الإصدار: 0.1
- تاريخ الإعداد: 2026-10-28
- المرجع: `SPECIFICATIONS.md`، خصوصًا متطلبات Firebase والتتبّع اللحظي
- النطاق: تصميم منفصل للمراجعة؛ لا ينشئ موارد سحابية ولا يغيّر التطبيق.

## 1. قرارات وحدود التصميم

1. Firebase هو الخيار المبدئي، وليس قرارًا بتفعيل خدمة أو فوترة.
2. Firebase Authentication للهوية، وCloud Firestore للبيانات التشغيلية الأساسية.
3. يمكن استخدام Realtime Database لموقع المركبة الحي إذا اجتاز مراجعة التكلفة والاختبارات الأمنية. لا يُحسم الاختيار النهائي قبل تجربة معزولة.
4. العمليات الحساسة — اعتماد الكابتن، ربط ولي الأمر بالرحلة، بدء/إنهاء الرحلة، فرض/رفع تعليق استقبال الطلبات، والتدقيق — لا يقررها العميل وحده؛ تمر عبر جهة موثوقة مثل Cloud Functions/Cloud Run أو خادم مناسب، بعد مراجعة متطلبات الفوترة.
5. لا توجد في هذه المسودة قواعد جاهزة للنشر. أي مقاطع قواعد أدناه هي مواصفات سلوكية/شبه قواعد، ويجب تحويلها إلى قواعد Firebase قابلة للاختبار قبل الاستخدام.
6. لا تُخزّن بيانات أطفال أو عناوين فعلية أو إحداثيات حقيقية في مرحلة التصميم والاختبار.
7. لا يُعتمد أي حقل أو إجراء مالي كدليل على الدفع أو التسوية ما لم يصدر عن مزود الدفع والخادم الموثوق.

## 2. نموذج الأدوار

| الدور | نطاق الصلاحية المقترح |
|---|---|
| ولي الأمر (guardian) | قراءة ملفه وطلباته فقط، وقراءة حالة الرحلة وموقعها إذا كان مرتبطًا بها ومصرحًا له أثناء نشاطها |
| الكابتن (captain) | قراءة ملفه وتعديل حقول الملف المسموح بها؛ قراءة الطلبات المسندة إليه؛ إرسال تحديثات موقع للرحلة النشطة المسندة إليه وفق تحقق الخادم |
| الإدارة (admin) | صلاحيات إدارية محددة ومراجعة، عبر هوية موثقة وامتيازات ممنوحة خارج العميل |
| الخادم الموثوق (server) | تنفيذ انتقالات الحالة والتحقق من العلاقات الزمنية والصلاحيات وإنشاء سجلات التدقيق |

**مبدأ أساسي:** لا تُمنح صفة الإدارة اعتمادًا على قيمة يرسلها المستخدم أو حقل يستطيع تعديله بنفسه. تستخدم صلاحيات موثوقة (مثل custom claims) تُمنح من بيئة إدارية آمنة، مع مراجعة دورية.

## 3. مخطط Cloud Firestore المقترح

تُستخدم معرّفات عشوائية غير دالة على الهوية. الحقول أدناه حد أدنى مقترح، وليست تصريحًا بجمع كل البيانات.

### 3.1 `users/{uid}`
- `role`: guardian | captain | admin — تُضبط من جهة موثوقة فقط.
- `displayName`: اسم العرض الضروري للخدمة.
- `phoneVerified`: حالة تحقق يكتبها الخادم فقط.
- `accountStatus`: pending | active | suspended | closed — تغييرات الحالة الحساسة من الخادم.
- `createdAt`, `updatedAt`: توقيت خادم.
- لا يُخزن هنا رقم الهوية أو بيانات طفل ما لم تُثبت الضرورة النظامية، ويُحدد لها نطاق وصول واحتفاظ منفصلان.

### 3.2 `guardianProfiles/{uid}`
- `serviceArea`: مدينة/نطاق عام عند الحاجة.
- `preferences`: تفضيلات خدمة غير حساسة.
- لا تُخزن عناوين المنزل والمدرسة الدقيقة في ملف عام أو ملف يمكن للكباتن تصفحه جماعيًا.

### 3.3 `captainProfiles/{uid}`
- `publicProfile`: بيانات العرض الضرورية فقط.
- `verificationStatus`: pending | approved | rejected | expired؛ يكتبها فريق المراجعة/الخادم فقط.
- `serviceAreas`, `availabilityPreference`.
- `eligibilityStatus`: eligible | blocked | suspended؛ لا يستطيع الكابتن رفع block صادر عن الخادم.
- `blockReasonCode`, `blockedAt`, `lastTrustedLocationAt`: تُدار من الخادم.
- تفاصيل الترخيص والتأمين والمركبة تحفظ في مجموعة خاصة منفصلة، بصلاحيات ضيقة ومدة احتفاظ محددة.

### 3.4 `serviceRequests/{requestId}`
- `guardianUid`, `captainUid` (قد يكون null قبل الإسناد).
- `status`: draft | submitted | accepted | rejected | cancelled | completed.
- `serviceType`, `serviceArea`, `scheduleSummary`.
- `quotedAmount`, `currency`: بيانات عرض فقط؛ ليست إثبات دفع.
- `createdAt`, `updatedAt`, `statusChangedAt`: توقيت خادم.
- تفاصيل الموقع الدقيق تحفظ منفصلة ولا تُقرأ إلا عند تحقق الحاجة والصلاحية وبعد المرحلة المناسبة من قبول الطلب.

### 3.5 `trips/{tripId}`
- `requestId`, `guardianUid`, `captainUid`.
- `status`: scheduled | active | interrupted | completed | cancelled.
- `startedAt`, `endedAt`, `updatedAt`: يكتبها الخادم.
- `locationSharingStatus`: off | active | stale | stopped.
- `lastTrustedLocationAt`: يكتبها الخادم فقط.
- لا تسمح قواعد العميل بتغيير أطراف الرحلة أو جعلها active/completed أو تعديل أوقاتها مباشرة.

### 3.6 `tripLocations/{tripId}` أو مسار الموقع في Realtime Database
يُفضّل فصل بيانات الموقع المتغيرة بسرعة عن مستند الرحلة:
- `lat`, `lng`: إحداثيات صالحة ضمن الحدود الجغرافية.
- `accuracyMeters`: دقة الجهاز إن توفرت.
- `serverReceivedAt`: وقت استلام موثوق من الخادم، لا وقت جهاز الكابتن وحده.
- `sourceUid`, `tripId`: علاقة موثقة مع الكابتن والرحلة.
- `sequence` أو `clientCapturedAt`: حقول مساعدة للتحقق من التكرار/القدم، ولا تُعد وحدها مصدر الثقة.
- لا تُحتفظ بسجل مسار طويل افتراضيًا. تُحدد مدة الاحتفاظ والحذف قبل التشغيل.

### 3.7 `captainEligibility/{uid}`
حالة تشغيلية لا يكتبها الكابتن:
- `canReceiveRequests`: boolean.
- `reasonCode`: location_stale | account_review | safety_review | null.
- `lastTrustedLocationAt`, `updatedAt`.
- يُحسب القرار من الخادم؛ تغيير واجهة التوافر لا يتجاوز هذا القيد.

### 3.8 `auditLogs/{logId}`
- `actorUid`, `actorRole`, `action`, `targetType`, `targetId`.
- `reasonCode`, `createdAt` (توقيت خادم).
- لا تُتاح كتابة/قراءة عامة، ولا يستطيع المستخدم حذف سجلاته أو تعديلها.
- لا تُنسخ إحداثيات دقيقة أو بيانات أطفال إلى السجل إلا عند ضرورة مثبتة.

### 3.9 مجموعات خاصة اختيارية قبل الإنتاج
- `captainPrivateDocuments/{uid}`: بيانات التراخيص والتأمين والمركبة؛ وصول الإدارة المصرح بها فقط.
- `serviceLocations/{requestId}`: العناوين الدقيقة؛ ولي الأمر صاحب الطلب والخادم، والكابتن المسند إليه فقط عند تحقق شروط المرحلة.
- `billingRecords/{recordId}`: مراجع مزود الدفع وحالات موثقة من خادم/ويب هوك موثوق، لا بيانات بطاقات.
- `supportCases/{caseId}`: شكاوى وحالات سلامة بصلاحيات محددة.

## 4. علاقات الوصول المطلوبة

1. ولي الأمر يقرأ `serviceRequests` فقط إذا كان `guardianUid == auth.uid`.
2. الكابتن يقرأ الطلب إذا كان `captainUid == auth.uid`، وبالحقول اللازمة للطلب المسند إليه فقط.
3. ولي الأمر يقرأ موقع الرحلة فقط إذا كان `guardianUid` مطابقًا له، والرحلة نشطة وموقع المشاركة فعالًا، ولم تُنهَ أو تُلغَ الرحلة.
4. الكابتن يرسل الموقع فقط إذا كان `captainUid` مطابقًا له، والرحلة مسندة إليه ونشطة. يرفض الخادم الموقع إذا كان غير صالح أو خارج تسلسل/سياق الرحلة.
5. لا يمكن لأي مستخدم تعداد جميع المستخدمين أو الرحلات أو مواقع المركبات.
6. لا يملك العميل كتابة `role`, `verificationStatus`, `eligibilityStatus`, `canReceiveRequests`, `lastTrustedLocationAt`, `startedAt`, `endedAt`, أو سجلات التدقيق.
7. لا تمنح معرفات غير قابلة للتخمين صلاحية بحد ذاتها؛ كل قراءة/كتابة تحتاج تحققًا من الهوية والعلاقة.
8. صلاحية الإدارة لا تعني تلقائيًا الحاجة إلى الاطلاع على كل عنوان أو مسار موقع؛ تُفصل الصلاحيات حسب المهمة.

## 5. قواعد Firestore/Realtime Database — متطلبات سلوكية

هذه قائمة تحقق وليست قواعد قابلة للنشر:

- **الافتراضي رفض:** كل قراءة/كتابة مرفوضة ما لم توجد قاعدة سماح صريحة.
- **مصادقة:** لا وصول للبيانات الخاصة دون جلسة مصادقة صالحة.
- **الملكية:** مقارنة UID المسجل في المستند بـ `request.auth.uid`، لا بمعرّف يرسله العميل في جسم الطلب وحده.
- **حقول محمية:** رفض تغيير الدور، حالة التحقق، حالات الرحلة الحساسة، حالة الأهلية، التوقيتات الموثوقة، بيانات الدفع وسجل التدقيق من العميل.
- **تحقق البيانات:** التحقق من نوع الحقول والقيم المسموحة والحقول الإلزامية ومنع الحقول الزائدة الحساسة.
- **قصر الاستعلامات:** يجب أن تتوافق الاستعلامات مع قواعد الأمان؛ القواعد ليست مرشحًا يخفي السجلات غير المسموح بها بعد إرجاعها.
- **الموقع:** قراءة الموقع مشروطة برحلة نشطة وعلاقة ولي الأمر/الكابتن بها. الكتابة تمر عبر تحقق يمنع انتحال رحلة أخرى أو تجاوز حظر الكابتن.
- **الخادم الإداري:** صلاحيات Admin SDK تتجاوز قواعد قاعدة البيانات؛ لذلك يجب حمايتها في الخادم، وتقليل الوصول إليها، واختبار كل endpoint يستخدمها.
- **حماية إساءة الاستخدام:** حدود معدل تحديث الموقع والطلبات، والتحقق من القيم، ومراقبة المحاولات المرفوضة.
- **لا أسرار في العميل:** لا تُضمّن مفاتيح خدمة أو أسرارًا إدارية في `index.html` أو المستودع.

## 6. آلية انقطاع الموقع وتعليق قبول الطلبات

1. عند بدء الرحلة عبر انتقال حالة موثوق، يفعّل الخادم مشاركة الموقع للرحلة المحددة.
2. يقبل الخادم تحديثًا فقط من الكابتن المسند إليه، مع إحداثيات صحيحة ووقت استلام موثوق.
3. إذا لم يصل تحديث موثوق خلال **دقيقتين** من آخر تحديث موثوق، يغيّر الخادم حالة الموقع إلى stale ويمنع الكابتن من تلقي طلبات جديدة.
4. يجب أن يفحص مسار إسناد/قبول كل طلب `captainEligibility.canReceiveRequests == true`؛ لا يكفي تغيير الحالة الظاهرة في الواجهة.
5. لا يستطيع الكابتن إزالة التعليق. يُرفع تلقائيًا أو بعملية خادم موثقة فقط بعد استعادة تحديثات موثوقة والتحقق منها، مع تسجيل السبب والوقت.
6. فقد الموقع لا يلغي الرحلة النشطة تلقائيًا. يرى ولي الأمر آخر موقع موثوق مع وقت واضح وتنبيه أن الموقع غير مباشر، وتُتبع آلية السلامة والتواصل المعتمدة.
7. يجب التمييز قدر الإمكان بين GPS غير متاح، وصلاحية معطلة، وانقطاع الشبكة. لا يمكن للمنصة ضمان منع المستخدم من تعطيل GPS أو الإنترنت؛ الضمان الممكن هو فرض قيود الخادم عند غياب التحديثات.
8. يجب تحديد وتيرة التحديث وحدودها واستهلاك البطارية والبيانات قبل التنفيذ، واختبار استعادة الاتصال وتكرار الرسائل وتأخرها.

## 7. دورة حياة الرحلة

- `scheduled → active`: الخادم يتحقق من إسناد الرحلة وأهلية الكابتن ويثبت `startedAt` ثم يفعّل الموقع.
- `active → interrupted`: حالة تشغيلية عند فقد التحديثات؛ لا تعني إنهاء الرحلة.
- `interrupted → active`: بعد التحقق من عودة الموقع الموثوق، مع إزالة التعليق وفق سياسة الخادم.
- `active/interrupted → completed` أو `cancelled`: انتقال موثوق ينهي مشاركة الموقع فورًا ويمنع قراءاته الجديدة؛ تنفذ إزالة/انتهاء صلاحية بيانات الموقع حسب سياسة الاحتفاظ.
- تُرفض الانتقالات غير المسموحة، والتوقيتات المستقبلية أو المعدلة من العميل، وتغيير أطراف الرحلة بعد إنشائها دون مسار إداري موثق.

## 8. اختبارات أمنية إلزامية قبل أي بيانات حقيقية

| الاختبار | النتيجة المطلوبة |
|---|---|
| ولي أمر يطلب رحلة/موقع ولي أمر آخر | رفض |
| كابتن يقرأ طلبًا غير مسند إليه | رفض |
| مستخدم غير مصادق يحاول قراءة بيانات خاصة | رفض |
| كابتن يغيّر `role` أو `verificationStatus` أو `canReceiveRequests` | رفض |
| كابتن يرسل موقعًا لرحلة أخرى أو بعد انتهائها | رفض |
| ولي أمر يطلب موقع رحلة منتهية/ملغاة | رفض القراءة الحية |
| لا تصل تحديثات موثوقة لأكثر من دقيقتين | تعليق استقبال الطلبات الجديدة من الخادم |
| الكابتن يغيّر التوفر يدويًا بعد التعليق | يبقى الحظر فعالًا |
| عودة موقع موثوق بعد الانقطاع | استعادة وفق قواعد الخادم مع سجل تدقيق |
| محاولة قراءة/تعديل سجل التدقيق | رفض المستخدم العادي |
| محاولة تغيير مبلغ/حالة دفع من العميل | رفض |
| انتهاء الرحلة | إيقاف مشاركة الموقع وعدم إظهار موقع حي لاحق |
| استعلام واسع لجلب جميع الرحلات/المواقع | رفض أو إرجاع فقط النطاق المصرح به وفق القاعدة |
| فحص قواعد المحاكي | جميع اختبارات السماح والرفض تمر قبل اعتماد القواعد |

يُفضّل استخدام Firebase Emulator Suite وبيانات اصطناعية لاختبارات القواعد قبل الاتصال بمشروع حقيقي. لا يُنشأ مشروع لهذا الغرض إلا بعد موافقة مستقلة.

## 9. الخصوصية والاحتفاظ

قبل الإنتاج، يلزم اعتماد سياسة صريحة تشمل: الغرض من جمع الموقع، إشعار وموافقة الأطراف، من يمكنه الاطلاع عليه، مدة الاحتفاظ، الحذف، التعامل مع الشكاوى والحوادث، ومراجعة المتطلبات السعودية ذات الصلة. لا تُحدد هذه المسودة مدة نهائية دون قرار واعٍ ومراجعة نظامية.

## 10. مراجعة التكلفة قبل التنفيذ

- التحقق من حصص Firebase المجانية الحالية ومن شروط الفوترة لكل خدمة مطلوبة.
- حساب عدد المستخدمين والرحلات وتكرار تحديث الموقع وحجم القراءات والكتابات المتوقعة.
- تحديد هل تتطلب آلية المراقبة كل دقيقتين وظيفة مجدولة أو خادمًا دائمًا أو آلية بديلة، وتقييم تكلفتها واعتماديتها.
- تقدير تكاليف الخرائط وأي رسائل SMS/OTP وتخزين المستندات والسجلات.
- وضع تنبيهات ميزانية وحدود استخدام وخطة إيقاف، مع فهم أن التنبيهات لا تضمن دائمًا منع الرسوم.
- عدم تفعيل الفوترة أو أي خدمة مدفوعة قبل عرض التقدير والموافقة الصريحة.

## 11. نقاط تحتاج قرارًا قبل تحويل المسودة إلى تنفيذ

1. هل تُخزّن العناوين الدقيقة في Firestore منفصلًا أم عبر خادم فقط؟
2. ما سياسة الاحتفاظ بالموقع بعد انتهاء الرحلة، مع مراعاة السلامة والخصوصية؟
3. ما وتيرة تحديث الموقع المقبولة، وما الحد الأقصى للبطارية والبيانات؟
4. ما آلية التحقق من ترخيص الكابتن والمركبة والجهة المخولة بمراجعة المستندات؟
5. ما نطاق صلاحيات الإدارة وسجل التدقيق؟
6. ما المتطلبات النظامية ومزود الدفع المناسبان قبل إطلاق الخدمة؟
7. بعد قياس التكلفة، هل تُستخدم Realtime Database للموقع أم بديل آخر؟

## 12. ما لم يحدث

- لم يُنشأ مشروع Firebase ولم تُربط حسابات.
- لم تُفعّل خدمة أو فوترة أو خرائط أو رسائل.
- لم تُضف مفاتيح أو أسرار.
- لم يُعدّل `SPECIFICATIONS.md` أو `index.html`.
- لم يُنشر التطبيق ولم تُستخدم بيانات حقيقية.
- هذه الوثيقة لا تعني اعتماد التصميم أو السماح بالتنفيذ؛ الخطوة التالية هي مراجعتها وتصحيحها بموافقة صاحب المشروع.
